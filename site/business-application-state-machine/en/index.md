# Business application state machine

> Source: `W-anp-P71` state-machine explicitisation (internal planning, not public). Code source of truth:
> `src/Portal.Components/PortalBusinessApplicationTransitions.cs`.
> Criteria source: internal benchmark study (the four "initially complete" criteria: explicit transition table,
> fail-closed before write, every transition writes an event, and a documented state flow).

## 1. Status vocabulary

| Status (constant) | Meaning |
| --- | --- |
| `Draft` | Draft |
| `Submitted` | Submitted; sits in the pending-review window |
| `InReview` | Under review; also sits in the pending-review window |
| `Returned` | Returned to the applicant for additions |
| `Approved` | Approved |
| `Rejected` | Rejected |
| `Withdrawn` | Withdrawn |
| `Closed` | Closed / archived |

The status set is guaranteed jointly by `PortalBusinessApplicationStatuses` and the database constraint
`CK_PortalBiz_BusinessApplications_Status` (the two must agree).

**Terminal states**: this state machine has **no** dedicated terminal-state constant and no `IsTerminalStatus` predicate; the
transition table shows that `Approved` / `Rejected` / `Closed` / `Withdrawn` currently have **no outgoing actions** at all, so
those four are the de-facto terminal states. That conclusion follows from "no row in the transition table has them as its
source", **not** from a terminal-state function.

## 2. Actions

| Action (constant) | Meaning | In the transition table? |
| --- | --- | --- |
| `Approve` | Approve | ✅ review path |
| `Return` | Return | ✅ review path |
| `Reject` | Reject | ✅ review path |
| `Close` | Close / archive | ✅ review path |
| `Resubmit` | Applicant resubmits (added in `W71`) | ✅ **self-service path**, not part of the back-office review predicate |
| `Submit` | Submit the application | ❌ handled by `SubmitApplication` (creates the application and writes the event); it does not go through the review transition path |
| `Claim` | Claim | ❌ not wired up yet (constant only) |
| `Withdraw` | Withdraw | ❌ not wired up yet (constant only) |
| `CreateDraft` | Create a draft | ❌ creation only; not a transition path |

Actions absent from the transition table are labelled as such; a "constant exists" is never passed off as an "implementation exists".

## 3. Legal transition table (single source of truth)

These 9 transitions are the **single source of truth** for the state machine, defined in
`PortalBusinessApplicationTransitions.All`:

| Current status | Action | Target status | Path |
| --- | --- | --- | --- |
| `Submitted` | `Approve` | `Approved` | review |
| `InReview` | `Approve` | `Approved` | review |
| `Submitted` | `Return` | `Returned` | review |
| `InReview` | `Return` | `Returned` | review |
| `Submitted` | `Reject` | `Rejected` | review |
| `InReview` | `Reject` | `Rejected` | review |
| `Submitted` | `Close` | `Closed` | review |
| `InReview` | `Close` | `Closed` | review |
| `Returned` | `Resubmit` | `Submitted` | **applicant self-service** |

- `MapActionToStatus(actionKey)` is derived from this table (each action has exactly one target).
- The SQL write guard predicate of `ReviewApplication` is generated by `BuildSqlStatusPredicate()` **from the same table**
  (**review-path actions only**), so it cannot drift from the table; `Resubmit`, whose `ViaReviewPath = false`, is kept out of
  that predicate so a self-service action cannot be triggered accidentally by the back-office review path.
- A unit test asserts the generated predicate is **semantically equivalent** to the hand-written window
  `IN (N'Submitted', N'InReview')` that existed before the explicitisation.

**Existing semantics preserved (important)**: `Close` is allowed only from `Submitted` / `InReview`, **not** from `Approved` /
`Rejected`. That was the pre-existing behaviour and is kept as-is here; changing it is a separate decision (needing migration
and regression), and the equivalence unit test guards the current behaviour.

## 4. Enforcement

1. **Explicit server-side gate**: `ReviewApplication` first maps the action to a target status via the transition table; an
   unknown action returns "unsupported action" and never reaches the write.
2. **Database guard**: the `WHERE` predicate of the SQL `UPDATE` (generated from the transition table) re-validates the current
   status at write time; a zero-row update advances nothing and writes no orphan event.
3. **Self-service actions on a separate path**: `ResubmitApplication` puts the **ownership** (`ApplicantUserId`) and **status**
   (`Returned`) conditions in one and the same `UPDATE` statement, eliminating the "read then write" TOCTOU window; it writes
   no reviewer fields.
4. **Constraint-driven field handling**: `CK_PortalBiz_BusinessApplications_ReviewState` requires `ReviewedUtc` and
   `ReviewedByUserId` to be **NULL** in the `Submitted` status, so `ResubmitApplication` **must clear both review fields** when
   it sets the status, or the constraint rejects it outright. `ReviewComment` is not constrained and is preserved; the
   authoritative history is carried by the transition events.
5. **Authorisation**: review actions remain governed by the back-office page's existing permission gates (application
   view / review / manage permission keys); the transition table governs only status legality and does not replace
   authorisation.

## 5. Every transition writes an event

Every transition that **actually happens** writes one `PortalBiz_WorkflowEvents` record carrying
`BusinessKind = BusinessApplication`, `ActionKey`, `FromStatus`, `ToStatus` and an operator trace. The SQL batch writes events
only over the `OUTPUT` set that was actually updated — **a zero-row update writes no orphan event**. `Resubmit` also writes
that event (`ActionKey = Resubmit`).

## 6. Relationship to the collaboration-item state machine

The two are **structurally isomorphic** (each has a transition-table class, plus mapping and SQL guard derived from the table,
plus a mandatory transition event), but **semantically independent**: collaboration items have 8 statuses / 8 actions /
15 transitions, while business applications have 8 statuses / 5 table actions / 9 transitions. They share neither status
vocabulary nor action constants (`PortalCollaborationItemActions` and `PortalWorkflowActions` are two separate constant sets).

## 7. Out of scope / known gaps

- **The UI entry point for `Resubmit`**: the data layer and contract are done; the front-end button is a UI change and needs a
  prototype plus confirmation first (AGENTS.md).
- **`Submit` / `Claim` / `Withdraw` are not in the transition table**: see section 2 — labelled as not wired up, out of scope
  for this round.
- **Changing the legal source statuses of back-office review actions** (e.g. whether `Close` should be allowed from
  `Approved`): a separate decision; the current behaviour is kept for this round.
- **The legacy business-application sample**: this state machine **is** the explicitisation of `BusinessApplicationDb` (the old
  P19 sample); there is no "second business-application state machine".
- This round **adds or removes no statuses** and changes no business semantics and no UI.
