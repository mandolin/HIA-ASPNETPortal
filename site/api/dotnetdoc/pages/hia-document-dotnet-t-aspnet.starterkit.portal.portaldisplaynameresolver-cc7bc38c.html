PortalDisplayNameResolver

class ASPNET.StarterKit.Portal.PortalDisplayNameResolver

按界面文化解析数据库承载的显示名（中文列 / 英文列 / 其它语言 JSON 列）。

Resolves database-carried display names (Chinese column / English column / other-languages JSON column) by UI culture.

remarks

存在理由：门户壳层与模块正文走 `App_GlobalResources/lang.*` 资源，而页签名（`PortalCfg_Tabs.TabName`）与 模块标题（`PortalCfg_Modules.ModuleTitle`）是数据库单列文本，**不随语言切换**，于是同一张卡片里出现 "英文标题 + 中文正文"的中英混排。本解析器把这两类文本接入与资源同源的文化判定，混排才有解。 列设计（用户 2026-10-18 裁定）：中文一列、英文一列、其它所有语言合并为一个 JSON 列。 中文列复用既有列（`TabName` / `ModuleTitle`）而不是新增列 —— 既有列 `NOT NULL` 且是所有渲染点的默认来源， 复用它才能保证"永远有值可显示"。 解析顺序： 1. 两字母语言码 `zh`（含 zh-CN / zh-TW 等区域变体）→ 中文列，缺失回落英文列； 2. 两字母语言码 `en` → 英文列，缺失回落中文列； 3. 其它文化 → JSON 列按"完整文化名 → 父文化名 → 两字母码"三级匹配； 4. 三级都未命中 → 回落中文列 → 回落英文列 → 空字符串。 该回退链与既有 `PortalNavigationEntry.GetDisplayName` 的语义一致（中文文化取中文、英文文化取英文、 一侧缺失回落另一侧），避免两套显示名解析逻辑对同一文化给出不同结论。 证明边界：本类型只证明"按文化选出最合适的显示文本"，**不证明**文本本身翻译正确、 JSON 键是受支持的文化（键名白名单属于语言管理功能），也不做任何授权判断。

Reason it exists: the portal shell and module body text come from `App_GlobalResources/lang.*` resources, while tab names (`PortalCfg_Tabs.TabName`) and module titles (`PortalCfg_Modules.ModuleTitle`) are single-column database text that **does not follow the language switch**, producing "English title + Chinese body" inside one card. This resolver connects those texts to the same culture decision the resources use, which is what makes the mixing fixable. Column design (user decision, 2026-10-18): one Chinese column, one English column, and one JSON column for every other language. The Chinese side reuses the existing columns (`TabName` / `ModuleTitle`) rather than adding new ones — those columns are `NOT NULL` and are the default source of every renderer, so reusing them guarantees there is always something to display. Resolution order: 1. two-letter language code `zh` (including zh-CN / zh-TW and other regional variants) → Chinese column, falling back to the English column when missing; 2. two-letter code `en` → English column, falling back to the Chinese column when missing; 3. any other culture → three-tier JSON lookup "full culture name → parent culture name → two-letter code"; 4. no hit → Chinese column → English column → empty string. That fallback chain matches the existing `PortalNavigationEntry.GetDisplayName` semantics (Chinese cultures take the Chinese name, English cultures the English one, and a missing side falls back to the other), so two display-name resolvers cannot disagree about the same culture. Proof boundary: this type proves only that "the most suitable display text was selected for the culture". It does **not** prove the text is a correct translation, that JSON keys are supported cultures (that allowlist belongs to language administration), and it makes no authorization decision.
