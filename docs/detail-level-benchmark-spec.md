# 细节级对标规范

阶段：[W-anp-P59](../work-zone/dev/plans/W-anp-P59.md)（`C-anp-P10`）
日期：2026-09-26
依据：`C-anp-P10` Q4 裁定（一手官方优先、标注来源强度、不适用清单）与用户对"不仅大块对标，**细节条目也要深度调研与深度对标**"的要求

## 一、目的

确保每个功能在**落地前**不仅有"有没有该功能"的宏观对标，更在**设计与体验的每个细节条目**上有可核查的对标依据——把"对标"从一次性调研，变成**可复用、可验收的工程规范**。

核心原则：**先有对标依据，再落地实现**（不得未对标就实现）。

## 二、适用范围

所有功能的实现与打磨（`C-anp-P11` 起，含 `P13` 体验打磨）。每个用户可见功能/交互改动，均须按本规范产出对标证据。

## 三、对标维度（八项，逐条目填写）

| # | 维度 | 要回答的问题 |
| --- | --- | --- |
| 1 | **设计意图** | 这个功能/交互为什么存在？解决什么真实问题？外部同类如何定位它？ |
| 2 | **预期效果** | 用户完成后得到什么？成功如何体现？ |
| 3 | **流程** | 步骤顺序、分支条件、异常路径是否清晰且可完成？ |
| 4 | **交互** | 控件选择、反馈时机、状态可见性、禁用/加载/空态如何处理？ |
| 5 | **操作体验** | 效率（步骤数/默认值）、可撤销、与站内其他功能是否一致？ |
| 6 | **异常与反馈** | 错误消息是否可理解、可行动？是否可恢复？是否泄露内部细节？ |
| 7 | **可达性（a11y）** | 键盘可达、焦点顺序、对比度、标签与语义化、旧浏览器基线（IE9+） |
| 8 | **双语一致性** | `zh-CN` / `en-US` 文案、术语与 `<lang>` 注释是否一致且同步？ |

> 除上述八项外，若涉及安全（认证/授权/审计/文件）还须追加"**安全事实**"维度（不写敏感数据、失败可审计等）。

## 四、每个维度的填写要求

对每个维度必须给出四项内容：

1. **现状**：本项目当前实现（代码/界面事实，不臆断）。
2. **对标对象**：外部具体产品/标准/规范（**一手官方优先**：Microsoft Learn、OWASP、NIST、W3C/WCAG、官方产品文档）。
3. **来源强度**：`一手` / `二手` / `社区` / `自有判断`——必须标注。
4. **差异与决定**：`- 采纳`（照做）/ `- 调整`（采纳但改造）/ `- 不采纳`（说明理由并入不适用清单）。

## 五、证据形式

- 一手来源须给出 **URL + 引用要点**（可核查）。
- **不得用二手推断冒充一手**；无法取得一手时，如实登记 **`待核实`**，并只用该来源已确证的层面下结论（不逐条断言）。
- 不适用项必须进**不适用清单**并写明原因（不得以"不需要"一笔带过）。

## 六、输出模板

```
### <功能名> —— <维度名>

- 现状：<代码/界面事实>
- 对标对象：<产品/规范名>（来源强度：<一手|二手|社区|自有>）
  - 引用：<URL> —— <要点摘录>
- 差异：<与现状的具体差异>
- 决定：<采纳 | 调整（如何改） | 不采纳（理由）>
- 不适用清单：<如有>
```

## 七、可执行的检查表（验收用）

- [ ] 八个维度**逐条**填写，无留空
- [ ] 每个维度都有**对标对象**与**来源强度**
- [ ] 一手来源附 **URL + 要点**；无一手者明确标 `待核实`
- [ ] 每个差异都有**决定**（采纳/调整/不采纳），不采纳者已在**不适用清单**说明
- [ ] 涉及安全的补了"安全事实"维度（不写口令/令牌/连接串/敏感 PII；失败可审计）
- [ ] 双语维度已确认 `zh-CN`/`en-US` 与 `<lang>` 注释同步
- [ ] a11y 维度已考虑键盘、对比度、标签与 IE9+ 基线

## 八、与工程流程的衔接

1. **实现前**：功能进入实现阶段前须完成本规范的对标产出（作为阶段 intake 的一部分）。
2. **验收时**：阶段 closeout 需附对标证据（检查表全绿）。
3. **复用**：本规范为通用模板；各阶段（数据范围、状态机、消息、文件、审计等）直接引用，不重复定义。

## 九、后续候选

1. 将检查表固化为脚本化门禁（如文档 inventory 类工具）。
2. 建立"对标证据索引"，按功能维度检索。
3. 与 UI 原型/设计稿流程联动（原型阶段即产出对标）。
