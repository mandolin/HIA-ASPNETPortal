# Developer guide

## Environment requirements

Recommended:

- A Windows development environment.
- Visual Studio 2022, or a Visual Studio able to build .NET Framework 4.8 projects.
- .NET Framework 4.8 Developer Pack.
- NuGet package restore capability.
- SQL Server or SQL Server LocalDB.
- IIS Express.
- Node.js and npm, only when you need to maintain the frontend asset build.
- For VSCode, the `Csharp_Webform` Profile is recommended, with C#, .NET Runtime and this project's recommended extensions enabled.

## Getting dependencies

This project uses the classic NuGet `packages.config`. The recommended path is to open `src/master.sln` in Visual Studio and enable NuGet Restore.

VSCode / command line:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File dev\scripts\Restore-NuGetPackages.ps1
```

`nuget.exe` is not currently on the ordinary PowerShell PATH. The script prefers the NuGet CLI; if it is not installed but `src\packages` already exists, the explicit restore is skipped so the legacy project stays buildable as it is. For a future full restore, install the NuGet CLI or use Visual Studio's NuGet Restore.

## Build

Recommended:

1. Open `src/master.sln` in Visual Studio.
2. Restore NuGet packages.
3. Select `Debug|Any CPU`.
4. Build the solution.

VSCode / command line:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File dev\scripts\Build-Solution.ps1 -Configuration Debug -Platform "Any CPU"
```

The script locates MSBuild from Visual Studio / Build Tools via `dev\scripts\Find-MsBuild.ps1`. It has been verified to find an installed MSBuild automatically and complete a `Debug|Any CPU` build; the actual install path varies with the local Visual Studio / Build Tools setup.

## Documentation sub-site build

The sub-site pages (the mirror pages under `site/`) are generated by the build script from `docs/` and `site/_translations/`:

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -File dev/scripts/Build-PortalSite.ps1
```

Two **read-only** switches (neither touches `site/`, so you can look before you leap):

- `-DryRun`: only reports "what would be generated" (new / content changed / unchanged) and writes **not a single byte** (directory creation included) — use it to rehearse a build before deciding to run it for real;
- `-OutputRoot <dir>`: writes the output to the given directory while still reading the real `site/` as input, so you can compare "what should be generated now" without touching the working tree (this is exactly how the mirror-freshness gate works).

## VSCode tasks

`.vscode/tasks.json` provides these common tasks:

- `nuget: restore packages`: restore or check NuGet packages.
- `build: solution Debug`: build `src/master.sln`, and acts as the default build task.
- `iisexpress: start Portal (40001)`: start `src/Portal` on the fixed port `40001`.
- `iisexpress: stop Portal (40001)`: stop only IIS Express processes matching the port or site path.
- `iisexpress: restart Portal (40001)`: run stop then start in sequence.
- `gulp: assets:build`: run the frontend asset build once.
- `gulp: startWatch` / `gulp: stopWatch`: keep the original Gulp watch tasks available from VSCode.
- `portal: build assets and start`: build the solution, build frontend assets and start IIS Express.
- `portal: documentation baseline`: emit a documentation inventory JSON of tracked sources.
- `portal: build JavaScript documentation pilot`: generate and verify the HIA JSDoc pilot standalone.
- `portal: build .NET DotNetDoc pilot`: generate and verify the HIA DotNetDoc pilot standalone.
- `portal: verify .NET XML documentation`: after a Debug build, check the existing C# XML documentation output.
- `portal: verify frontend contracts`: read-only check of tracked Web Forms presentation, themes, module CSS and Gulp contracts.
- `portal: verify public documentation`: read-only check of public Markdown entry points, relative file links, privacy boundaries and generated-directory boundaries.

These tasks only call helper scripts and npm scripts inside the repository and do not modify `.sln`, `.csproj` or `.csproj.user`, so they do not overwrite Visual Studio's existing debug settings.

## VSCode debugging

`.vscode/launch.json` provides two debug configurations:

- `Portal: Start IIS Express (40001), then attach`: start IIS Express, then attach to `iisexpress.exe` through the process picker.
- `Portal: Attach to IIS Express`: for manual attachment when IIS Express is already running.

Usage:

1. Open the Debug panel in VSCode.
2. Select `Portal: Start IIS Express (40001), then attach`.
3. When the process picker appears, select `iisexpress.exe`.
4. Visit `http://localhost:40001/` in a browser.
5. After debugging ends, `iisexpress: stop Portal (40001)` runs.

IIS Express has been verified to return `HTTP 200 OK` at `http://localhost:40001/`.

To reach IIS Express from a Win7 VM or another LAN device you cannot use the default simple localhost mode. Stop any existing instance first, then bind the host IP explicitly:

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -File dev\scripts\Stop-IISExpress.ps1 -Port 40001
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -File dev\scripts\Start-IISExpress.ps1 -Port 40001 -HostName 192.168.199.21
```

The script keeps the `localhost` binding and also prints the external URL. If the VM still cannot connect, follow the script's hint and add a URLACL or firewall rule in an elevated host command prompt. Without `-HostName` the original localhost startup is used, leaving Visual Studio and VSCode debug paths untouched.

## Independent modules (capabilities provided outside the core)

The portal supports deploying business capabilities as **independent modules**: a package lives under `DesktopModules/<package>/` and is loaded by the hosting mechanism according to the trusted catalog, the deployment profile and the package enable state, so the core needs no code change for each new capability. Form Builder is the first example of this mechanism.

### Package manifest (module.json)

Every package directory must contain `module.json` whose fields match the runtime validation rules:

```json
{
  "schemaVersion": 2,
  "packageId": "HIA.FormBuilder",
  "displayName": "表单构建器（独立模块）",
  "version": "1.0.0",
  "minimumPortalVersion": "1.0",
  "moduleKind": "Independent",
  "desktopEntry": "DesktopModules/FormBuilder/FormBuilder.ascx",
  "resources": ["Styles/FormBuilder.css"],
  "capability": { "capabilityId": "BasicBusiness.FormBuilder", "role": "Primary" }
}
```

Key constraints (a mistake makes the package **silently stop rendering**, invisible to builds and unit tests):

- `schemaVersion` must be a JSON **integer** `1` or `2`, never a string.
- `desktopEntry` must stay inside this package directory and the entry file must exist.
- `resources` must be **package-relative** paths with an extension in `.css`/`.png`/`.jpg`/`.jpeg`/`.gif`/`.webp`, whose files exist; a `DesktopModules/...` full path is invalid.
- `capability` must be an **object** with `capabilityId` and `role`; the capability key must be registered in the authoritative `PortalCapabilityRegistry`, and the role must be one of `Primary`/`Contributor`/`Projection`/`Adapter`/`Block`. Top-level `capabilityId`/`capabilityRole` is invalid.
- Fields such as `script`/`scripts`, `externalUrl`/`externalUrls`, `assembly`/`assemblies` and `packageUrl` are prohibited: a manifest declaration cannot change execution or download capability.
- `moduleKind` may only be `Core` (the default) or `Independent`.

### Deployment profile allow-lists

The active profile comes from `Portal.ModuleProfiles.Active` in `Web.config`, then at start-up is overlaid in "base configuration plus environment override" order from `Config/appSettings.json` and `Config/appSettings.<environment>.json`. Every active profile's `Portal.ModuleProfiles.<Profile>.Packages` allow-list must **explicitly list** the `packageId` of an `Independent` module; the `*` wildcard covers only the `Core` form and must never implicitly allow an independent module.

After changing an allow-list, restart the site (or trigger an application-domain recycle) for the new configuration to take effect. `Config/appSettings.dev.json` is a machine-local ignored file; register the change in `Config/appSettings.json` and `Config/appSettings.*.template.json` so other environments do not miss the package.

### Install and uninstall

The reusable implementation is `IPortalModuleProvisioner` / `PortalModuleProvisioner`, which writes or clears `PortalCfg_Tabs`, `PortalCfg_ModuleDefinitions`, `PortalCfg_Modules` and `PortalCfg_ModulePackageStates` with idempotent SQL. At deployment time you can run the scripts directly:

```powershell
# Install (idempotent)
sqlcmd -S "(localdb)\MSSQLLocalDB" -d Portal -i src\Setup\PortalCfg_FormBuilder_Provision.sql
# Uninstall (reverse cleanup)
sqlcmd -S "(localdb)\MSSQLLocalDB" -d Portal -i src\Setup\PortalCfg_FormBuilder_Deprovision.sql
```

The uninstall script removes the module instance, reclaims a definition no longer referenced, deletes the package-state row, and removes the dedicated tab when it no longer hosts any module. Reverting the profile allow-list and removing physical files are deployment actions outside the SQL scripts.

### Security boundary

- A third-party module must **never** obtain the `Admins` role or an administrative capability. Installation performs a fail-closed check on the capability id: unregistered capabilities (capability self-creation) and administrative permission-key prefixes are rejected.
- Source and capability declarations are never an authorization basis. A module instance's role settings (such as `EditRoles`) only decide who may edit that instance's content; they do not grant the module itself administrative permission.
- A single module's installation failure does not affect other modules; runtime rendering failures are isolated by the host and do not fail the whole page.

### Theme skins and legacy-browser compatibility

When adding visible elements, supply `body.portal-theme-<theme> .<module-class>` scope rules in the `Default.css` of all six official skins, plus the `Default` fallback skin. Colours, borders and typography come from the theme layer through `--portal-*` semantic variables with legacy-kernel fallbacks; module-private CSS owns layout only and must not rely on flex/grid, `rem`, `calc` or other layouts unsupported by IE9, nor use raw colour literals outside `var()`.

### Verification

- Static contract gate: `dev/scripts/Test-PortalIndependentModuleGate.ps1` (L0, validating manifest contracts, profile allow-lists, the Admins boundary, uninstall symmetry and six-skin scope rules).
- Browser-level runtime evidence: `dev/scripts/Invoke-PortalIndependentModuleRuntimeEvidence.ps1` drives `Test-PortalIndependentModuleRuntimeEvidence.mjs` and needs a running site, LocalDB, `mise`-provided node and development-only playwright. It collects screenshots and assertions for light/dark themes and Chinese/English locales; pass an output directory through the `-OutputDirectory` parameter for the artifacts.

## Online capabilities (online install/upload)

Online capabilities mean installing or uploading a capability package (a `.zip` archive) into the portal host through a controlled channel without breaking existing security or approval boundaries. The carrier base, isolation channel, two-step confirmation gate, audit, signature and integrity checks, malware scanning, and rollback with failure isolation are all implemented in `Portal.Components` and `Portal` and verified by quality gates and unit tests.

### Carrier base and isolation channel

Isolation staging policy constants live in `src/Portal.Components/PortalOnlinePackagePolicy.cs` (package extension, maximum package bytes, maximum entry count, and per-entry / total-decompressed byte caps) together with the isolation staging virtual directory (under `~/App_Data/OnlinePackages/Staging`). The isolation stager `src/Portal.Components/PortalOnlinePackageStaging.cs` has `TryStage` decompress under an isolated sub-directory; on any failure it cleans up the current upload's own sub-directory in a `finally` block, so one failed upload never pollutes the core directory or another upload.

### Two-step confirmation gate

`PortalOnlinePackageConfirmationGate` in `src/Portal.Components/PortalOnlinePackageConfirmation.cs` provides a stateless two-step confirmation: `TryIssue` issues a ticket (nonce against replay, synchronization token against CSRF, package-hash binding, idempotent), and `TryConfirm` confirms the ticket under a second authentication step. The permission keys are `Module.OnlinePackage.Upload` and `Module.OnlinePackage.Confirm`, both in the Module domain.

### Audit

`src/Portal.Components/PortalOnlinePackageAuditEvents.cs` defines the online-capability audit event vocabulary (upload validated / install confirmed / staged discarded / rollback drill); the runtime wrapper in `src/Portal/Components/PortalOnlinePackageAudit.cs` writes through the existing `PortalOperationAudit.Record` into `PortalCfg_OperationAudits`, recording a truthful `outcome` (including failures) rather than faking success.

### Signature and integrity checks

`src/Portal.Components/PortalOnlinePackageIntegrity.cs` provides SHA-256 byte/stream computation (same convention as offline assembly-state checks) and genuine RSA-SHA256 signature verification, and carries the integrity duty that .NET Framework 4.8 omits by not auto-validating CRC-32 when reading archives.

### Scanning and security gate

`src/Portal.Components/PortalOnlinePackageScanning.cs` exposes a single `IPortalOnlinePackageScanner` adapter point (where an enterprise intranet scanner can be wired in), a default `PortalOnlinePackageUnavailableScanner` that is explicitly "not wired", and the joint gate `TryAllowInstall` (allowlist → integrity → signature → scan; any failure rejects, and early failures short-circuit).

### Rollback and failure isolation

## Two-level grouped main navigation

The main navigation renders two levels: a group header plus the in-group tab links. It is **not** a parent/child tab tree: `PortalCfg_Tabs` gained no parent column, groups are a presentation-only functional family, they take no part in authorization, and the tab visibility chain is unchanged.

The vocabulary is a closed set in `src/Portal.Components/PortalNavigationGroupAlias.cs`, fixed to four groups by `SortOrder`:

| Stable key | Chinese label | English label | Default members (`NavigationKey`) |
| --- | --- | --- | --- |
| `WorkAndApproval` | 工作与审批 | Work & Approvals | `MyWorkItems`, `LeaveAndExpense` |
| `Business` | 业务办理 | Business | `BusinessRequests`, `MyProfile` |
| `PortalAndHelp` | 门户与帮助 | Portal & Help | `Home`, `Help` |
| `SystemAdministration` | 系统管理 | System Administration | `Admin`, `CapabilityWorkbench` |

The rendering chain has three layers with strictly separated responsibilities:

- `PortalNavigationGroupView` is a pure-logic view model. It consumes the tab collection after role filtering and entry gating, and produces groups, flat ungrouped tabs, a degradation flag and an empty-group count. It preserves each tab's display index in the final collection, so `tabindex` semantics match the pre-change behaviour.
- `DesktopPortalBanner.ascx` renders group headers as native `<button type="button">` elements carrying `aria-expanded` and `aria-controls`; in-group entries remain flat `.portal-tab` links, and the selected state is a non-link span. No `menu` / `menubar` role and no inline `onclick` are used. The server emits every group expanded, so tabs stay reachable without JavaScript.
- `Scripts/Navigation/PortalNavigationGroups.js` is an ES5 progressive-enhancement script that binds collapse/expand clicks, `Escape` close-and-return-focus, and `aria-expanded` synchronisation. It changes presentation state only and never re-evaluates permissions.

Alias overrides use the configuration key `Portal.Navigation.GroupAliases` (Web.config appSettings, overridable by the database runtime setting), with a comma-separated `NavigationKey=GroupKey` value. Parsing is strict: an unknown group key, a malformed entry or a duplicate key **rejects the whole configuration and falls back to the default vocabulary**; the renderer sees the degradation flag and returns to the retained flat `DataList`. Invalid configuration never hides a tab.

Theme layers cover **7 skins** (six official skins plus the `Default` fallback; the `ThemeProbe` diagnostic probe is excluded), each defining `body.portal-theme-<name> .portal-nav-group*` scope rules. The class family is `portal-nav-group`, `portal-nav-group-toggle`, `portal-nav-group-tabs`, `portal-nav-group-caret`, `portal-nav-group-count` and `portal-nav-group-hidden`. `:focus` must give a visible outline, and the hidden class must use `display:none` so in-group links leave the keyboard Tab sequence. Apply the same rule when adding visible elements; do not write rules only in a module-local stylesheet.

Gates and evidence:

| Gate / evidence | What it proves |
| --- | --- |
| `dev/scripts/Test-PortalNavigationGroupContract.ps1` (L0) | Vocabulary covers the eight seeded `NavigationKey` values, configuration key registered in four places, fail-closed parsing, no authorization symbols in groups, theme-settings inbound link |
| `dev/scripts/Test-PortalNavigationGroupRender.ps1` (L0) | Disclosure markup semantics, seven-skin scope rules, ES5 script constraints, degradation rollback wiring |
| `dev/scripts/Test-PortalAccessibilityBaseline.ps1` (L0) | A1–A10: contrast >= 4.5, `:focus`, `img alt`, no inline `onclick`, named anchors, plus grouped-navigation assertions and the `a11y-runtime` uncovered-ledger lock |
| `dev/scripts/Test-PortalNavigationGroupRenderEvidence.mjs` (L2) | Browser level: separate Chinese/English screenshots, collapse/expand clicks, `Escape` focus return, computed styles across seven skins, tabs reachable with JavaScript disabled |
| `dev/scripts/Test-PortalCollaborationRuntimeEvidence.mjs` (L2) | Collaboration workbench four quadrants (light/dark theme x Chinese/English locale) each with its own screenshot, never shared |

## Configuration notes

- `src/Portal/Config` contains `*.template.*` files as well as real environment files.
- Before changing real configuration, confirm whether you should be changing the template instead.
- Connection strings are no longer written to `UnityCfg*.xml`; they are read from the external `{ExternalCfgPath}\{env}\connectionStrings.config`.
- When `ExternalCfgPath` is empty, `{current process user directory}\Web\HIA-ASPNETPortal\` is used by default.
- The local `dev` default file path is `{current process user directory}\Web\HIA-ASPNETPortal\dev\connectionStrings.config`.
- The logical name currently used in `connectionStrings.config` is `Portal`, mapped after startup to Unity's `connectionString` named instance; `providerName` is required and the portal's main business database is fixed to `System.Data.SqlClient`.
- The environment variable `HIA_ASPNETPORTAL_CONNSTR_PORTAL` can override the concrete connection string value; the external file itself must still exist.
- Do not commit real production connection strings, accounts, passwords, tokens or certificates.
- `.gitignore` already covers some configuration, database and build-output ignore rules, but historical files still need manual review.
